# Реструктуризация раскладки по шаблону {{template}}

Беклог операции реструктуризации: путь от порождённой миграции до дерева, приведённого
к новому шаблону пути.

Реструктуризация меняет правило вывода пути, а не данные записей: фасеты прежние, а целевые
пути вычислены по новому шаблону. Перечень «откуда куда» лежит в файле миграции и здесь
не повторяется — миграция остаётся единственным носителем раскладки.

Значения операции несёт фронтматтер — второй раз они не собираются
(BKL-005; текст нормы — `backlog norms --rule BKL-005`). Задачи исполняются
по порядку.

Порядок исполнения — отметки задач, выводимый признак «выполнено ранее», стоп-знак перед
необратимой задачей — задан BKL-006 (`backlog norms --rule BKL-006`)
и BKL-007 (`backlog norms --rule BKL-007`), а его носитель —
`{{runner}}`: прочитать его перед первой задачей; здесь он
не пересказывается (BKL-008; текст нормы — `backlog norms --rule BKL-008`). Указатель носителя несёт
и фронтматтер значением `runner`: оттуда его читает проверка, отсюда — исполнитель.

## 2. Остановка окружения

- [ ] 2.1 Остановить окружение каждого проекта, каталог которого переносит накат: работающий
  контейнер держит привязку к прежнему пути, и после наката сервисы работают с каталогом,
  которого больше нет. Условие лежит в тексте задачи: есть файл описания сервисов в каталоге
  проекта — сервисы останавливаются, нет — задача отмечается неприменимой.

  Средств виртуализации в контейнере агента нет, поэтому команду исполняет владелец на хосте,
  а агент её передаёт — по каталогу на проект:

  ```bash
  docker compose -f <каталог проекта>/docker-compose.yaml down
  ```

  Команда с удалением томов здесь не называется и не исполняется: она превращает остановку
  в потерю данных. Парного подъёма задача не несёт: окружение поднимает владелец, когда
  сочтёт нужным.

  - Проверка: сервисы проектов переносимых операций ({{operations}}) не запущены; тома не удалялись
  - Выполнено ранее: сервисы переносимых проектов не запущены

## 3. Накат реструктуризации

- [ ] 3.1 **Стоп-знак.** Показать владельцу версию миграции `{{version}}`, число переносимых
  записей — {{operations}} — и то, что накат трогает каталоги всех названных записей сразу,
  а не одной: перекладка по шаблону меняет место каждому проекту, чей путь от целевого
  отличается. Назвать необратимость для внешних ссылок — клонов, настроек среды разработки,
  локальных скриптов — и отослать к файлу миграции как к перечню «откуда куда». Дождаться
  подтверждения, записать его во фронтматтер в `confirmed.apply` и накатить:

  ```bash
  bash tools/host-runner/call.sh layout-apply VERSION={{version}}
  ```

  - Проверка: `exit: 0`, каталоги лежат по целевым путям операций, поля `path` их записей
    приведены, версия `{{version}}` числится в `layout/applied.yaml`, а журнал операций
    несёт событие `MigrationApplied`
  - Выполнено ранее: версия `{{version}}` есть в `layout/applied.yaml`
- [ ] 3.2 Прогнать проверку моделей после наката:
  `bash tools/host-runner/call.sh registry-lint`
  - Проверка: код возврата `0`: пути записей приведены и каталоги по ним существуют
  - Выполнено ранее: проверка состояния — повторяется без последствий
