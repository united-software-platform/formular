## Кейс 1. Понять, нужен ли моей операции беклог

**Когда.** У меня есть операция — выпуск версии, переименование репозитория, миграция базы,
развёртывание стенда — и я решаю, заводить ли ей шаблон.

**Что делаю.** Отвечаю на один вопрос: есть ли в операции необратимый шаг либо шаг, выполнимый
только мной? Если нет ни того, ни другого — беклог ей не нужен
([BKL-001](../rules/operation-backlog-rules.md#беклог-как-носитель-порядка)).

| Операция | Беклог | Почему |
|----------|--------|--------|
| Выпуск версии с публикацией тега | нужен | Публикация необратима для внешних ссылок |
| Переименование репозитория | нужен | Переименование делает владелец, агент не вправе |
| Миграция схемы базы | нужен | Прежнее состояние встречным действием не возвращается |
| Сборка образа из `Dockerfile` | не нужен | Повторяется целиком, следа не требует |
| Прогон тестов | не нужен | Состояния не меняет |

**Что получаю.** Решение. Операции без необратимого и без владельческого шага носитель порядка
для одного вызова превращается в обёртку: её след оставляет собственный вывод прогона.

## Кейс 2. Поставить механизм в свой проект

**Когда.** Проект решил применять беклоги. Нужны Claude Code и `python3`; сторонних зависимостей
ядро не требует.

**Что делаю.** Три шага, подробности каждого — в [README](../README.md#установка-в-проект).

Первый — плагин, из любой оболочки, где есть `claude`:

```bash
claude plugin marketplace add united-software-platform/formular
claude plugin install backlog@formular
```

Второй — вход. **В сеансе Claude Code имя `backlog` разрешается само, и шаг не нужен**: каталог
входа включённого плагина платформа кладёт на путь поиска инструмента Bash сеанса. Моей оболочке
его не кладёт никто, поэтому ей вход даёт обёртка, которую кладёт подъём:

```bash
backlog link                 # из сеанса Claude Code: имя уже разрешается
```

Если Claude Code живёт в контейнере, сеанс моего домашнего каталога не видит, и обёртка, положенная
из сеанса, до моего терминала не доезжает. Тогда подъём идёт в моей оболочке — **путём каталога
поставки**, потому что имени там ещё нет. Путь печатает `backlog where` в сеансе:

```bash
<каталог поставки>/bin/backlog link
```

Третий — нормы, из корня проекта (в сеансе либо в своей оболочке после подъёма):

```bash
backlog install              # нормы и образцовый шаблон — в дерево проекта
```

**Что получаю.** В дереве проекта появляются четыре файла: нормы
`rules/operation-backlog-rules.md`, глоссарий `docs/glossary.md`, описание каталога следа
`backlog/README.md` и образцовый шаблон `templates/sample-operation.md`. В `CLAUDE.md`
дописываются строки `@`-импортов — так нормы попадают в контекст агента; в `.gitignore` —
пути следа. Рядом ложится манифест `.backlog-manifest.json` со слепком каждого файла.

**Повторный прогон состояния не меняет.** Файл, который я правил сам, прогон не перезаписывает:
он называет расхождение, ставит прочие файлы и оставляет решение мне.

> **Внимание:** `backlog link` в моём терминале до подъёма отвечает `backlog: команда
> не найдена` — и это не отказ подъёма, а его предусловие: обёртки ещё нет, а имя разрешается
> только в сеансе. Первый вызов идёт либо из сеанса, либо путём каталога поставки; дальше имя
> разрешается и в терминале.

**Признак установки.** `backlog where` печатает каталог поставки, а в корне проекта лежат
`.backlog-manifest.json` и `rules/operation-backlog-rules.md`.

## Кейс 3. Пройти сквозной прогон на образцовой операции

**Когда.** Механизм поставлен, и я хочу увидеть всю работу целиком, прежде чем писать свой шаблон.

**Что делаю.**

```bash
backlog generate --operation sample-operation \
  --value target="поставка плагином" --no-flag host-part
```

**Что получаю.** Путь порождённого файла и сам файл по адресу
`backlog/sample-operation/<штамп>/tasks.md`. Во фронтматтере — значения операции, в тексте —
задачи группами. Вот его начало как оно есть:

```markdown
---
template_version: "1.0.0"
generated: "2026-10-09"
operation: sample-operation
subject: "20261009120943"
target: поставка плагином
confirmed:
  irreversible_step: null
---
```

Дальше — задачи. Каждая несёт отметку, строку проверки и признак «выполнено ранее»:

```markdown
- [ ] 1.3 Убедиться, что предмет операции `поставка плагином` существует и пригоден к работе
  - Проверка: предмет найден, препятствий к шагу 2 не названо
  - Выполнено ранее: проверка состояния — повторяется без последствий
```

Затем прошу агента исполнить беклог — [кейс 6](#кейс-6-исполнить-беклог-агентом) — и по завершении
проверяю полноту:

```bash
backlog verify backlog/sample-operation/<штамп>/tasks.md
```

## Кейс 4. Написать шаблон своей операции

**Когда.** Образцовая операция показала грамматику, и я завожу рабочую операцию проекта. Шаблон —
файл в каталоге `templates/`, и **его имя есть имя операции**: файл `templates/release.md` делает
вызываемым `--operation release`.

**Что делаю.** Собираю шаблон из пяти частей.

### Маркер версии и фронтматтер

Первая строка шаблона называет его версию — её порождённый беклог несёт в себе, чтобы было
видно, каким составом задач он порождён:

```markdown
<!-- template_version: 1.1.0 -->
---
template_version: "{{template_version}}"
generated: "{{date}}"
operation: {{operation}}
subject: "{{subject}}"
runner: "{{runner}}"
target: {{target_scalar}}
confirmed:
  irreversible_step: null
---
```

Подстановки `{{date}}`, `{{operation}}`, `{{subject}}`, `{{runner}}`, `{{template_version}}`
и `{{rules}}` заполняет порождение — вызывать их значения не нужно. `{{target}}` — моё значение,
его даёт `--value target=...`. Парная подстановка `{{target_scalar}}` — тот же текст в виде,
пригодном значением фронтматтера: в тексте задач ставлю `{{target}}`, во фронтматтере —
`{{target_scalar}}`, и о кавычках думать не приходится.

Поля `confirmed.*` оставляю пустыми: в них исполнитель запишет подтверждения владельца.

### Задача

Задача — три строки: отметка с текстом, проверка и признак «выполнено ранее». Признак
отвечает на вопрос «как узнать, что это уже сделано», и пишется прозой — его сверяет
исполнитель, а не проверка:

```markdown
- [ ] 1.2 Прогнать структурную проверку этого беклога
  `backlog lint <путь этого беклога>`
  - Проверка: код возврата `0`, расхождений проверка не называет
  - Выполнено ранее: проверка состояния — повторяется без последствий
```

### Стоп-знак

Необратимую задачу открываю словом **Стоп-знак** и называю последствия прямо — что изменится,
в каком объёме и возможен ли возврат. Исполнитель запросит подтверждение непосредственно перед
ней и запишет его во фронтматтер:

```markdown
- [ ] 2.1 **Стоп-знак.** Показать владельцу предмет `{{target}}`, предмет беклога `{{subject}}`
  и то, что шаг необратим: вернуть прежнее состояние встречным действием нельзя. Дождаться
  подтверждения, записать его во фронтматтер в `confirmed.irreversible_step` и исполнить шаг
  - Проверка: подтверждение получено и записано, шаг исполнен
  - Выполнено ранее: состояние уже несёт результат шага — он состоялся
```

### Условный блок

Группа задач, нужная не всякому прогону, берётся в условный блок. Взведённый признак порождает
первую ветку, снятый — вторую:

```markdown
{{#host-part}}
- [ ] 3.1 Передать владельцу перечнем команд то, что исполняется на хосте
  - Проверка: перечень команд сообщён владельцу
  - Выполнено ранее: перечень сообщён в этом сеансе
{{/host-part}}
{{^host-part}}
- [ ] 3.1 Хостовой части у этой операции нет: признак `host-part` снят вызовом
  - Проверка: решение о пропуске прочитано владельцем
  - Выполнено ранее: решение названо в этом сеансе
{{/^host-part}}
```

Снятая ветка не молчит, а называет пропуск: отсутствие строк читалось бы как забытая задача.

### Указатель носителя порядка

Текст шаблона ссылается на `{{runner}}` и первой задачей предписывает его прочитать. Порядок
исполнения в шаблоне не пересказывается: он живёт в навыке-исполнителе, и второй его носитель
разошёлся бы с первым
([BKL-008](../rules/operation-backlog-rules.md#передача-исполнения)).

**Что получаю.** Файл `templates/<операция>.md`, пригодный к порождению. Проверяется он первым
порождением: подстановка без значения или неназванный признак останавливают прогон кодом `2` —
дефект виден до исполнения операции, а не посреди него.

## Кейс 5. Породить беклог своей операции

**Когда.** Шаблон написан, операция запускается.

**Что делаю.**

```bash
backlog generate --operation release \
  --subject v1.4.0 \
  --value target="formular" --value version="1.4.0" \
  --flag publish-tag --no-flag host-part
```

- `--subject` — предмет беклога. Без него предметом становится штамп прогона `YYYYMMDDHHMMSS`:
  так адресуется операция, которую я вправе повторить над тем же предметом. Операцию, выполнимую
  над своим предметом однажды, адресую предметом предметной области — как `v1.4.0` выше.
- `--value ключ=значение` — повторяется по значению.
- `--flag` и `--no-flag` — признаки условных блоков. **Называются все**: признак, не названный
  вовсе, оставляет маркер блока в тексте и останавливает порождение.

**Что получаю.** Файл `backlog/release/v1.4.0/tasks.md` и его путь в выводе.

**Если не вышло.** Коды возврата отвечают, что делать:

| Код | Что значит | Что делаю |
|-----|------------|-----------|
| `0` | Беклог порождён — или уже лежал по этому адресу | Исполняю лежащий файл, он неизменён |
| `1` | Ввод не позволяет породить: значение названо дважды, предмет непригоден сегментом пути | Правлю вызов |
| `2` | Ошибка окружения: шаблона нет, подстановка без значения, признак не назван | Правлю шаблон или вызов |

> **Важно:** порождённое не перезаписывается. Повторный вызов над занятым адресом отвечает путём
> лежащего файла и оставляет его как есть — поэтому прогон, который я хочу начать заново, получает
> новый предмет, а не правку старого беклога.

## Кейс 6. Исполнить беклог агентом

**Когда.** Беклог порождён, пора его исполнять.

**Что делаю.** В сеансе агента зову носитель порядка исполнения и называю путь:

```text
/backlog:backlog-run исполни backlog/release/v1.4.0/tasks.md
```

**Что получаю.** Агент читает беклог целиком, идёт по задачам сверху вниз и для каждой:

- сверяет признак «выполнено ранее» с состоянием — выполнен, значит задача пропускается
  и отмечается;
- исполняет задачу, если признак не выполнен;
- проверяет её по строке проверки и ставит отметку `- [x]`;
- дописывает добытые значения во фронтматтер — беклог остаётся исполнимым в другом сеансе.

Перед задачей со стоп-знаком агент останавливается и спрашивает меня, называя последствия прямо.
**Утверждение беклога подтверждением не является** — спрашивают именно перед шагом, потому что
значения необратимой задачи на момент порождения могли ещё не существовать. Мой отказ прекращает
исполнение: беклог линеен, последующие задачи не исполняются, а уже выполненное не отменяется.

По завершении агент прогоняет `backlog verify` и называет итог: что исполнено, что осталось мне,
путь беклога и вердикт проверки.

## Кейс 7. Продолжить прерванный прогон

**Когда.** Сеанс оборвался, агент сменился, прогон встал посреди операции.

**Что делаю.** Зову исполнение по тому же пути — ровно как в [кейсе 6](#кейс-6-исполнить-беклог-агентом).
Ни отката, ни второго беклога не требуется.

**Что получаю.** Исполнение продолжается с задачи, признак которой не выполнен: исполненное
распознаётся по состоянию и пропускается. Значения берутся из фронтматтера и второй раз
не собираются, поэтому сеанс порождения и сеанс исполнения могут не совпадать.

> **Важно:** при расхождении отметки в беклоге с состоянием верно **состояние**. Отметка
> переживает откат, ручную правку и прерванный сеанс, а состояние — нет
> ([BKL-006](../rules/operation-backlog-rules.md#признак-исполнения)).

## Кейс 8. Проверить беклог

**Когда.** Хочу знать, цел ли беклог и исполнен ли он.

**Что делаю.**

```bash
backlog lint   backlog/release/v1.4.0/tasks.md    # структура
backlog verify backlog/release/v1.4.0/tasks.md    # структура и полнота исполнения
```

**Что получаю.**

- `lint` отвечает на вопрос, цела ли грамматика: фронтматтер несёт версию шаблона и указатель
  носителя порядка исполнения, остатков грамматики шаблона в тексте нет, каждая задача несёт
  проверку и признак «выполнено ранее», файл завершается таблицей версий. Этим же прогоном
  проверяется порождение — до записи файла.
- `verify` добавляет полноту исполнения: закрыты ли отметки и заполнены ли подтверждения
  владельца там, где исполнена задача со стоп-знаком. Его зовут по завершении исполнения.

Коды возврата: `0` — расхождений нет, `1` — расхождения названы, `2` — ошибка вызова
или окружения.

**Чего проверка не делает.** Состояния она не видит и признак «выполнено ранее» не сверяет —
он проза. Поэтому расхождение она называет, но не правит: названное возвращает меня к сверке
признака с состоянием — отметить либо исполнить, — а не прекращает операцию.

## Кейс 9. Положить след и шаблоны не по умолчанию

**Когда.** Каталог `backlog/` в корне проекта мне не подходит: след нужен вне репозитория,
а шаблоны лежат в своём каталоге.

**Что делаю.** Каждый каталог называется ключом вызова либо переменной окружения:

```bash
backlog generate --operation release --root /var/lib/backlog --templates ops/templates
```

```bash
export BACKLOG_ROOT=/var/lib/backlog
export BACKLOG_TEMPLATES=ops/templates
```

**Что получаю.** Умолчания — каталоги `backlog` и `templates` в корне проекта; корень проекта
вход находит сам — по манифесту установки или каталогу системы контроля версий вверх по дереву.
Поэтому прогон из подкаталога второго каталога следа не заводит. Корень можно назвать и прямо —
переменной `CLAUDE_PROJECT_DIR`, там где маркеров нет.

## Кейс 10. Обновить механизм и нормы

**Когда.** Вышла новая версия поставки.

**Что делаю.**

```bash
claude plugin update backlog@formular
backlog install
```

**Что получаю.** Первый вызов переписывает каталог поставки — вход и навык обновлены. Второй
доводит до дерева проекта нормы: файл, слепок которого совпал с записанным в манифест,
обновляется; файл, который я правил сам, прогон называет расхождением и не трогает.

Обёртку входа после обновления поднимать заново не нужно: она разрешает каталог поставки в момент
вызова, а не несёт записанный путь — путь установки содержит версию и устарел бы первым же
обновлением.

> **Внимание:** нормы правятся **в источнике поставки**, а не в дереве проекта. Правка файла
> на месте прогон не переживает иначе как расхождением: он назовёт файл и оставит его как есть,
> а новая версия нормы до проекта не доедет.

## Кейс 11. Изменить состав задач операции

**Когда.** Посреди прогона выяснилось, что задач не хватает или они не те.

**Что делаю.** Правлю **шаблон** и поднимаю его версию. Лежащий беклог не правлю.

**Что получаю.** Правка действует на следующие прогоны операции, а не задним числом
на состоявшиеся: беклог назвал версию шаблона, которой порождён, и остаётся свидетельством
того прогона ([BKL-004](../rules/operation-backlog-rules.md#порождённое-не-правится)).
Текущий прогон либо доисполняется как есть, либо прекращается — и запускается заново
с новым предметом.

Правкой не считается ход исполнения: отметки задач и значения, дописываемые во фронтматтер,
беклог исполняют, а не переписывают его состав.

## Кейс 12. Разобраться, почему вход не зовётся

**Когда.** Вызов в терминале отвечает `backlog: команда не найдена` либо прогон не находит
каталог поставки.

**Что делаю.** Сперва различаю два отказа — они требуют разного.

| Отказ | Что означает | Чем закрывается |
|-------|--------------|-----------------|
| `backlog: команда не найдена` | В этой оболочке нет обёртки: имя разрешается само только в сеансе Claude Code. Плагин при этом может быть установлен | Подъём обёртки — из сеанса либо путём каталога поставки |
| `каталог поставки беклога не найден` | Обёртка лежит, а разрешать ей нечего: плагин снят, выключен либо его каталог этой оболочке недоступен | `BACKLOG_HOME` либо включение плагина |

Подъём первого раза именем не зовётся — только путём:

```bash
<каталог поставки>/bin/backlog link      # из моей оболочки, имени ещё нет
backlog link                             # из сеанса Claude Code, имя разрешается
```

Каталог поставки печатает `backlog where` в сеансе. Дальше проверяю, что подъём состоялся:

```bash
backlog where            # печатает каталог поставки
```

**Что получаю.**

- `link` кладёт обёртку в `~/.local/bin/backlog` (каталог меняется ключом `--bin-dir`) и сам
  называет, лежит ли этот каталог на пути поиска моей оболочки; не лежит — печатает строку,
  которой это закрывается. Повторный прогон состояния не меняет.
- Каталог поставки обёртка ищет каждый вызов, тремя способами по порядку: переменная
  `BACKLOG_HOME`, перечень `claude plugin list --json`, раскладка кеша плагинов
  `CLAUDE_CODE_PLUGIN_CACHE_DIR`. Записанным путём она его не несёт намеренно — путь установки
  содержит версию и устарел бы первым обновлением. Ни один способ не сработал — прогон печатает
  каждый и останавливается:

```bash
BACKLOG_HOME=<каталог поставки> backlog where
```

Два случая, когда `BACKLOG_HOME` нужен постоянно — его место тогда в файле профиля оболочки:
источником плагина служит каталог репозитория (раскладки кеша у такой поставки нет) либо
`claude` в этой оболочке недоступен, как на хосте при Claude Code в контейнере.

- Если сборка окружения нужна, а средств нет, прогон перечисляет испробованные способы (`uv`,
  `venv`, внешний `pip`) и чем каждый закрыть. Пока файл зависимостей пуст, окружение
  не собирается вовсе — ядро обходится стандартной библиотекой.
