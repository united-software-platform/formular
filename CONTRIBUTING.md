## Устройство репозитория

Поставка — каталог плагина [`plugin/backlog/`](./plugin/backlog):

| Что | Где в поставке |
|-----|----------------|
| Манифест плагина | [`.claude-plugin/plugin.json`](./plugin/backlog/.claude-plugin/plugin.json) |
| Вход командной строки | [`bin/backlog`](./plugin/backlog/bin/backlog) |
| Домен, сценарии и адаптеры | [`src/backlog/`](./plugin/backlog/src/backlog) |
| Сборка окружения | [`lib/python-env.sh`](./plugin/backlog/lib/python-env.sh) |
| Порядок исполнения | [`skills/backlog-run/`](./plugin/backlog/skills/backlog-run/SKILL.md) |
| Приёмка шаблона | [`skills/backlog-template/`](./plugin/backlog/skills/backlog-template/SKILL.md) |
| Образцовый шаблон | [`templates/`](./plugin/backlog/templates) |
| Нормы беклога и глоссарий | [`share/`](./plugin/backlog/share) |

Принадлежность репозитория, в поставку не входящая:

| Что | Где |
|-----|-----|
| Запись источника плагина | [`.claude-plugin/marketplace.json`](./.claude-plugin/marketplace.json) |
| Шаблоны операций проекта | [`templates/`](./templates) |
| Каталог следа — порождённые беклоги, закрытые `.gitignore` | `backlog/` |
| Проверки ядра и входа | [`tests/`](./tests) |
| Окружение агента | [`docker-compose.yml`](./docker-compose.yml), [`Makefile`](./Makefile) |
| Образец плагина агента — экспортируемая спецификация архитектуры | [`docs/spec/agent-plugin-blueprint/`](./docs/spec/agent-plugin-blueprint/index.md) |

Ядру зависимостей не нужно — оно обходится стандартной библиотекой. Механизм сборки окружения
для зависимостей в поставке всё же есть: [`lib/python-env.sh`](./plugin/backlog/lib/python-env.sh)
собирает окружение интерпретатора, когда инструменту поставки зависимость потребуется.

## Правка поставки

Нормы и определения понятий существуют в одном экземпляре — в
[`plugin/backlog/share/`](./plugin/backlog/share), образцовый шаблон — в
[`plugin/backlog/templates/`](./plugin/backlog/templates). Копий в дереве репозитория нет:
[`CLAUDE.md`](./CLAUDE.md) подключает
[нормы](./plugin/backlog/share/rules/operation-backlog-rules.md) и [глоссарий](./plugin/backlog/share/docs/glossary.md)
прямо из источника, и правка видна контексту репозитория без установочного прогона.

Шаблоны операций проекта в [`templates/`](./templates) называют нормы кодом и вызовом
`backlog norms --rule BKL-NNN`, а не ссылкой на файл: так же, как шаблоны любого
проекта-потребителя.

Источником плагина [`.claude-plugin/marketplace.json`](./.claude-plugin/marketplace.json)
объявлен каталог `./plugin/backlog` этого же репозитория: плагин грузится из него на месте,
а не установкой самого себя, поэтому правка механизма доезжает до следующего сеанса без публикации
и без смены версии.

## Окружение разработки

Работа ведётся в контейнере агента: образ, тома и профили описывает
[`docker-compose.yml`](./docker-compose.yml), хостовую подготовку — [`Makefile`](./Makefile).

Полная подготовка — одна цель:

```bash
make init
```

Она выполняет хостовую часть (`.env` из [`.env.example`](./.env.example), каталоги `.ssh`
и `.claude-accounts`, записи в `.gitignore`, SSH-ключ проекта и конфигурация SSH для git-хоста),
а затем разворачивает инструменты SDD прогоном `openspec init` в контейнере.

Два обстоятельства, о которых цель не догадывается:

- `.env` нужен до первого запуска контейнера. Цель создаёт его из образца, но значения
  `GIT_HOST` и `CLAUDE_PROFILE` заполняет человек; без `.env` развёртывание инструментов SDD
  останавливается с ошибкой.
- Профиль аккаунта — каталог внутри `.claude-accounts/`, названный значением `CLAUDE_PROFILE`.
  Контейнеру монтируется только он: так профили соседних проектов не смешиваются, а чужие
  остаются скрытыми.

Маркетплейс репозитория объявлен в `.claude/settings.json` источником `directory` с абсолютным
путём `/app` — путём рабочего дерева в контейнере агента. Относительный путь документация
Claude Code для этого источника не описывает, поэтому вне контейнера путь заменяется локально —
в `.claude/settings.local.json` — либо плагин грузится ключом `--plugin-dir ./plugin/backlog`.

Хостовая часть повторяется отдельно, не затрагивая инструменты SDD, а инструменты обновляются
отдельно после смены версии OpenSpec в образе. Полный перечень целей печатает `make help` —
здесь он не повторяется, иначе разошёлся бы с `Makefile` при первой же правке.

## Проверки

Ядро и вход — грамматика шаблона, маркер версии, вид значения фронтматтера, запрет
перезаписи порождённого, каркас по кодам норм, выдача норм и образца, рекомендация
для `.gitignore`:

```bash
python3 -m unittest discover -s tests
```

Шаблон операции — приёмка по всем сочетаниям признаков, обязательна при правке шаблона
по [BKL-009](./plugin/backlog/share/rules/operation-backlog-rules.md#прогон-при-правке-шаблона):

```bash
backlog check-template templates/<операция>.md
```

`Makefile` — объём секций целей, обязателен при любой правке файла
по [MAKE-004](./rules/makefile-rules.md#локальный-прогон-проверки-make-004):

```bash
sh tools/make-lint/check.sh
```

Артефакты изменения OpenSpec — состав и связность:

```bash
openspec validate <имя изменения> --strict
```

## Образец плагина агента

[`docs/spec/agent-plugin-blueprint/`](./docs/spec/agent-plugin-blueprint/index.md) — архитектура
`backlog`, описанная как переносимое техническое решение. Другой проект строит по ней свой плагин
со своим предметом. `backlog` в ней — эталонная реализация: на него ссылаются по путям,
но требования из него не выводятся.

### Когда править спецификацию

Изменение плагина сверяется с решениями `APB-001`..`APB-012`, если оно затрагивает хотя бы одно:
поставку, вход, зависимости, слои и контракты ядра, нормы поставки, навыки, конвейер артефакта,
приёмку шаблона, адресацию или проверки.

| Что изменилось | Что править |
|----------------|-------------|
| Изменение укладывается в действующее решение | Ничего, кроме путей и имён в [эталонной реализации](./docs/spec/agent-plugin-blueprint/reference-implementation.md), если они поменялись |
| Изменение меняет решение | Запись решения в [`decisions.md`](./docs/spec/agent-plugin-blueprint/decisions.md) и связанные с ней строки [чек-листа](./docs/spec/agent-plugin-blueprint/conformance.md) |
| Эталон начал отступать от правила | Новая запись `APB-DNN` в [`deviations.md`](./docs/spec/agent-plugin-blueprint/deviations.md) |
| Отклонение эталона устранено | Статус записи `APB-DNN` и упоминание в воплощении соответствующего решения |

Пять отклонений `APB-D01`..`APB-D05` открыты: эталон пока отступает от CLAR и CQRS. Это готовые
задачи на выравнивание эталона по правилам.

У каждого файла спецификации своя таблица версий. Заголовки решений `APB-NNN` служат якорями
ссылок из чек-листа, отклонений и `README.md`, поэтому при правке заголовка нужно сверить ссылки.
Отдельной проверки ссылок в репозитории нет.

### Перенос в другой проект

1. Проверить, что в целевом проекте уже есть набор SDD Developer Kit и правила `rules/*`:
   спецификация ссылается на их коды и сама их не несёт.
2. Скопировать каталог `docs/spec/agent-plugin-blueprint/` в целевой проект по тому же пути,
   иначе относительные ссылки на `rules/` не разрешатся.
3. Поручить агенту пройти [чек-лист соответствия](./docs/spec/agent-plugin-blueprint/conformance.md)
   и выдать отчёт в его форме. По ходу проверки агент ничего не исправляет.
4. Исправления по отчёту вести отдельными задачами целевого проекта, в порядке решений
   от `APB-001` к `APB-012`.

> **Внимание:** перенесённая спецификация — снимок, а не установленная копия. Ни механизма
> обновления, ни манифеста у неё нет. Перенесённую версию называет последняя строка таблицы
> версий `index.md`, и правка образца здесь до целевого проекта сама не доходит.

## Правила и процесс

Правила репозитория лежат в [`rules/`](./rules) и подключаются в контекст агента
файлом [`CLAUDE.md`](./CLAUDE.md). [`AGENTS.md`](./AGENTS.md) — тот же свод для агентов,
`CLAUDE.md` не читающих: правка состава правил вносится в оба файла. Ничем это не проверяется,
и расходятся они молча.

Вопросы, которые возникают до первой правки, и нормы, которые на них отвечают:

| Вопрос | Норма |
|--------|-------|
| Как озаглавлен и чем наполнен коммит | [GIT-009](./rules/git-rules.md#формат-сообщения-коммита) |
| Откуда берутся код, номер и описание задачи | [GIT-010](./rules/git-rules.md#формат-сообщения-коммита) |
| Можно ли дописать подпись агента | [GIT-012](./rules/git-rules.md#запрет-служебных-подписей) |
| Что делать с незакоммиченными правками в файле | [GIT-020](./rules/git-rules.md#гейт-редактирования) |
| Чем завершается каждый документ | [DOC-022](./rules/documentation-rules.md#жизненный-цикл-документа) |
| Что делать с разросшейся целью `Makefile` | [MAKE-001](./rules/makefile-rules.md#норма-объёма-секции-make-001) |

Имя рабочей ветки — `{CODE}-NNN-{краткое-описание}`, код проекта `FRM`; шаблон задан
разделом «Процесс разработки» файла [`CLAUDE.md`](./CLAUDE.md). Полный состав норм — там же,
перечнем подключаемых правил.

Работа ведётся изменениями OpenSpec в три шага:

1. **Предложение** — навык `/openspec-propose`: предложение, решения и задачи изменения.
2. **Исполнение** — навык `/openspec-apply-change`: задачи проходятся по порядку.
3. **Архивация** — навык `/openspec-archive-change`: состоявшееся изменение уходит в архив,
   а спецификация принимает его дельту.

Предмет системы описан спецификациями
[`openspec/specs/backlog/`](./openspec/specs/backlog/operation-backlog/spec.md). Каталог
`openspec/changes/archive/` чтению не подлежит — [READ-004](./rules/reading-rules.md#запрет-каталогов-read-004).
