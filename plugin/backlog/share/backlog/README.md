# Беклоги операций

Каталог порождённых беклогов: по каталогу на операцию, внутри — по каталогу на предмет,
в каждом `tasks.md` с порядком работ и следом исполнения.

## Что здесь лежит

Путь беклога складывается из имени операции и её предмета: `<операция>/<предмет>/tasks.md`.
Предмет операции, повторяемой над одним и тем же предметом предметной области, — штамп прогона
`YYYYMMDDHHMMSS`: повторный прогон получает свой беклог, а не упирается в занятый адрес. Предмет
операции, выполнимой над своим предметом однажды, — предмет предметной области: второго порядка
работ у неё не бывает.

```text
backlog/
  sample-operation/<штамп>/tasks.md     образцовая операция
```

Корень этого каталога — умолчание входа, а не константа кода: вызов принимает `--root`, и каталог
следа принадлежит тому, кто продукт применяет. Сами беклоги в репозиторий не попадают — закрыты
`.gitignore`; этот документ оставлен исключением, потому что отвечает на вопрос об адресе,
а не хранит чей-то прогон.

Фронтматтер несёт значения исполнения — второй раз они не собираются. Дальше идут группы задач,
у каждой задачи проверка и признак «выполнено ранее». Необратимую задачу открывает стоп-знак:
она исполняется только после отдельного подтверждения владельца.

Беклог остаётся на своём пути и после исполнения: он отвечает на вопрос, как прошёл конкретный
прогон.

## Каким операциям нужен беклог

Тем, у которых есть необратимый шаг либо шаг, выполнимый только владельцем
([BKL-001](../rules/operation-backlog-rules.md#беклог-как-носитель-порядка)). Прочим операциям
носитель порядка для одного вызова превращается в обёртку.

## Откуда берётся

Беклог порождается входом, а руками не пишется
([BKL-003](../rules/operation-backlog-rules.md#порождение-прогоном)):

```bash
backlog generate --operation sample-operation \
  --value target=проба --flag host-part
```

Предмет называется ключом `--subject`; без него предметом становится штамп прогона. Признаки
условных блоков называются полностью — и взведённые `--flag`, и снятые `--no-flag`: признак,
не названный вовсе, оставляет маркер блока в тексте и прекращает порождение.

Состав вызова целиком — `backlog generate --help`. Вход поставляется плагином `backlog`,
и имя команды не зависит от того, куда плагин установлен. Исполняет беклог навык
`/backlog:backlog-run` — он же носитель порядка исполнения.

## Приёмка шаблона

Шаблон операции принимается прогоном, а не чтением глазами
([BKL-009](../rules/operation-backlog-rules.md#прогон-при-правке-шаблона)):

```bash
backlog check-template templates/sample-operation.md
```

Приёмка прогоняет шаблон по каждому сочетанию признаков условных блоков — взведённых
и снятых — и каждый вариант проверяет той же структурной проверкой, что и порождение. Значений
она не требует: подстановки, которые порождение не заполняет само, получают заглушку с именем
подстановки. Файла беклога приёмка не пишет — каталог следа после неё остаётся прежним.

Каждое расхождение названо с сочетанием признаков, на котором найдено; последняя строка —
вердикт: число вариантов и число расхождений. Коды возврата: `0` — шаблон принят, `1` — найдены
расхождения, `2` — ошибка вызова или окружения, в том числе шаблон без маркера версии или
с числом признаков больше восьми.

Пишет шаблон кто угодно — агент или внешний вызов. Навык `/backlog:backlog-template` проверяет,
нужен ли операции беклог, называет критерии ссылками на нормы и образец и принимает шаблон
этим прогоном.

## Чем проверяется

Беклог проверяется прогоном ([BKL-010](../rules/operation-backlog-rules.md#проверка-беклога)),
и проверок две:

```bash
backlog lint backlog/sample-operation/<предмет>/tasks.md      # структура
backlog verify backlog/sample-operation/<предмет>/tasks.md    # структура и полнота исполнения
```

`lint` отвечает, цела ли грамматика: фронтматтер несёт версию шаблона и указатель носителя
порядка исполнения, остатков грамматики шаблона в тексте нет, каждая задача несёт строку
проверки и признак «выполнено ранее», файл кончается таблицей версий. Сюда же входит каркас:
беклог ссылается на нормы исполнения — самодостаточность значений, признак исполнения,
стоп-знак, передачу исполнения, — первая задача называет носитель порядка исполнения, вторая —
прогон `backlog lint` этого беклога. Каркас проверяется по смыслу, а не дословным совпадением
с образцом. Эту же проверку прогоняют само порождение и приёмка шаблона — до записи файла,
поэтому беклог, не отвечающий структуре, на диске не появляется, а правится шаблон.

`verify` отвечает, исполнен ли беклог: все отметки закрыты, а подтверждения владельца
во фронтматтере заполнены там, где исполнена задача со стоп-знаком. Его прогоняет навык
исполнения перед тем, как итог уйдёт владельцу: отметка, не поставленная по исполненной задаче,
иначе остаётся необнаруженной.

Коды возврата: `0` — расхождений нет, `1` — расхождения найдены, `2` — ошибка вызова или
окружения. Найденное проверка называет, но не правит: состояния она не видит, и отметку
по домыслу не ставит — расхождение закрывает тот, кто беклог исполняет, сверкой признака
с состоянием.

На беклоге, порождённом прежней версией шаблона, `lint` может назвать расхождение: состав
беклога отвечает тому, чем он порождён, и задним числом такой файл не правится.

## Порождённое не правится

Беклог, порождённый прежним прогоном, задним числом не правится — ни по составу задач, ни
по вызовам, которые он называет
([BKL-004](../rules/operation-backlog-rules.md#порождённое-не-правится)). Поэтому в исполненных
беклогах остаются имена снятых инструментов: они фиксируют, чем операция была исполнена, а не
чем её исполнить сегодня. Текущий способ вызова называет этот документ.
