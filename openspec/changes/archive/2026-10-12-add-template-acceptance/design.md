# Design

## Context

Ядро беклога — пакет `plugin/backlog/src/backlog` без внешних зависимостей, разложенный по слоям:

- домен — `structure_findings` и `execution_findings` над разобранной структурой
  `BacklogDocument`/`BacklogTask`; о разметке домен не знает;
- приложение — сценарии `generate`, `lint`, `verify`, `install` и контракты чтения;
- инфраструктура — `load_template`, `render`, разбор `MarkdownBacklog`, файловые адаптеры;
- вход — `__main__.py`: значения, которые порождение выводит само (`date`, `run_stamp`,
  `operation`, `subject`, `runner`, `rules`, `<ключ>_scalar`), собираются здесь,
  `template_version` добавляет сценарий порождения.

Порождение уже делает ровно то, что нужно приёмке на одном варианте: `render` → `parse` →
`structure_findings` до записи файла. Девять шаблонов в `templates/` после FRM-010 несут один
каркас и проходят `generate` и `lint` во всех вариантах. Мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**

- приёмка шаблона одним вызовом, без значений и без записи файла;
- правила каркаса — единые для порождения, приёмки и проверок лежащего беклога;
- навык, который называет критерии и принимает работу, но не пишет шаблон сам.

**Non-Goals:**

- контракт шаблона и порождение шаблона из данных — рассмотрены и отвергнуты: приёмка
  прогоном делает их ненужными;
- проверка содержания задач — признак «выполнено ранее» и текст проверки остаются прозой;
- дословная сверка каркаса с образцом;
- правка шаблонов в `templates/` — они уже отвечают каркасу.

## Decisions

### Приёмка — отдельный сценарий слоя приложения

`CheckTemplateUseCase` принимает путь шаблона, получает версию и текст, перечень подстановок
и признаков, строит по варианту на каждое сочетание признаков и прогоняет каждый через
`render` → `parse` → `structure_findings`. Выход — число вариантов и расхождения
с сочетанием признаков каждого.

Альтернатива — ключ `--dry-run` у `generate`: отвергнута, потому что `generate` требует
значений и одно сочетание признаков, и ключ поменял бы смысл обязательных аргументов.

### Шаблон по пути — прежний адаптер

Путь разбирается на каталог и имя операции, и шаблон читается тем же `FileTemplates`:
маркер версии и отказ кодом `2` при его отсутствии приходят без нового кода. Нового контракта
чтения не заводится.

### Грамматика шаблона остаётся в инфраструктуре

Сбор подстановок и признаков — знание о `{{x}}`, `{{#x}}`, `{{^x}}` — живёт рядом с `render`
функцией `template_grammar(text)` и подаётся сценарию так же, как `render`. Домен грамматики
шаблона по-прежнему не знает.

### Значения приёмки собирает вход

Сбор значений, которые порождение выводит само, выносится из `generate` в общую функцию входа
и вызывается обеими подкомандами: два носителя одного перечня разошлись бы при первой правке.
Для приёмки предмет — фиксированная строка, ссылка на нормы считается от адреса беклога под
умолчанием корня следа. Прочие подстановки получают заглушку `<имя>`; к подстановке
`<ключ>_scalar` значение выводится от `<ключ>`, как в `_pairs`.

### Правила каркаса — в домене, по смыслу

`BacklogTask` получает поле `text` — текст задачи без разметки отметки, а `BacklogDocument` —
поле `rule_anchors` — якоря ссылок, найденные разбором. Домен держит перечень якорей норм
исполнения (`самодостаточность-значений`, `признак-исполнения`,
`стоп-знак-необратимой-задачи`, `передача-исполнения`) и строку вызова самопроверки
`backlog lint` и проверяет:

- каждый якорь перечня встречается в `rule_anchors`;
- текст первой задачи содержит значение `runner` из фронтматтера;
- текст второй задачи содержит `backlog lint`.

Нормы и имя самопроверки — знание о том, чем беклог обязан быть, а не о разметке, поэтому
место им в домене. Якорь, а не код `BKL-NNN`, выбран потому, что ссылка адресует раздел норм:
номер правила в тексте ссылки ничего не адресует.

Альтернатива — отдельные правила только в приёмке шаблона, без `lint`: отвергнута владельцем,
потому что структура при порождении и структура лежащего файла — одна проверка по BKL-010.

### Навык — критерии ссылками и приёмка прогоном

`skills/backlog-template/SKILL.md` устроен как `backlog-run`: нормы адресуются от корня
проекта (`${CLAUDE_PROJECT_DIR}/rules/...`), нормы называются кодом и ссылкой. Порядок навыка:

1. Проверка BKL-001 — вопросом владельцу о необратимом шаге и шаге владельца.
2. Выбор режима: новый шаблон (имя свободно, версия `1.0.0`) либо правка (версия лежащего
   шаблона запоминается до правки).
3. Критерии: нормы BKL-001..BKL-010 ссылками и путь образца `templates/sample-operation.md`.
4. Шаблон пишет вызывающий.
5. Приёмка: `backlog check-template <путь>`; при правке — сверка, что версия выросла.
6. Расхождение возвращает к шагу 4; код `0` — итог с путём шаблона.

Версия правленого шаблона сверяется с версией, прочитанной до правки, а не с историей git:
чтение истории без явного указания запрещает GIT-019.

## Risks / Trade-offs

- [Число вариантов растёт как 2ⁿ от числа признаков] → у шаблонов набора не больше одного
  признака; при числе признаков больше 8 приёмка отказывает кодом `2` с указанием числа —
  такой шаблон стоит разделить, а не перебирать.
- [Старые беклоги перестают проходить `lint` и `verify`] → незавершённых беклогов без каркаса
  в проекте нет; README поставки уже допускает расхождение на беклоге прежней версии шаблона.
- [Проверка по смыслу пропустит формально присутствующий, но бессодержательный каркас] →
  принято: приёмка отвечает за структуру, содержание остаётся за автором и владельцем.
- [Строка `backlog lint` в домене привязывает домен к имени команды] → имя команды названо
  нормой BKL-010 и меняется вместе с ней.

## Migration Plan

1. Правка ядра, тесты и навык в источнике плагина; версия плагина в манифесте поднимается
   до `1.2.0`.
2. Правка норм и README в `plugin/backlog/share/`, затем `backlog install` — установленные
   копии в `rules/` и `backlog/README.md` обновляются, манифест установленного переписывается.
3. Приёмка всех девяти шаблонов `templates/` новой подкомандой — должна дать `0`.

Откат — возврат коммитов изменения: формат шаблонов и беклогов не меняется.
