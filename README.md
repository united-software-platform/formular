## Что это

Беклог — носитель порядка работ одной операции и следа её исполнения. Он нужен операции,
у которой есть необратимый шаг либо шаг, выполнимый только владельцем: порядок, записанный
в беклоге, не теряется при обрыве, а каждая задача несёт проверку и признак «выполнено ранее»,
по которому исполненное распознаётся заново.

Система делает две вещи: порождает беклог по шаблону операции и несёт порядок, по которому
беклог исполняется. Исполняет его агент — по навыку `/backlog:backlog-run`.

Механизм поставляется плагином Claude Code: проект получает его установкой плагина, а нормы
и образцовый шаблон — прогоном `backlog install`.

Нормы беклога — в [правилах](./rules/operation-backlog-rules.md) (`BKL-001`..`BKL-010`),
понятия — в [глоссарии](./docs/glossary.md).

## Установка в проект

Нужны Claude Code и `python3` с модулем `venv`. Зависимости ставить не придётся: ядро
обходится стандартной библиотекой.

Плагин ставится из перечня источников этого репозитория, нормы — прогоном установки:

```bash
claude plugin marketplace add united-software-platform/formular
claude plugin install backlog@formular
backlog install
```

Перечень источников добавляется однажды на профиль: запись в конфигурации проекта объявляет
его имя, но пригодным к установке не делает. Источником может быть и каталог репозитория
вместо адреса на GitHub — тогда механизм берётся из рабочего дерева, и правки в нём доезжают
до следующего сеанса без публикации.

`backlog install` кладёт в дерево проекта нормы, определения понятий, описание каталога следа
и образцовый шаблон, дописывает строки `@`-импортов в `CLAUDE.md` и пути в `.gitignore`
и пишет манифест установленного `.backlog-manifest.json` со слепком каждого файла.

Повторный прогон состояния не меняет. Файл, слепок которого разошёлся с манифестом, прогон
не перезаписывает: расхождение значит, что файл правил сам проект, — путь называется, прочие
файлы устанавливаются, а решение остаётся владельцу.

## Возможности

| Вход | Что делает |
|------|------------|
| `backlog install` | Кладёт в проект нормы, определения понятий и образцовый шаблон |
| `backlog generate` | Порождает беклог операции по шаблону и значениям вызова |
| `backlog check-template` | Принимает шаблон операции: прогоняет его по всем сочетаниям признаков без записи файла |
| `backlog lint` | Проверяет структуру лежащего беклога |
| `backlog verify` | Проверяет структуру и полноту исполнения |
| Навык `/backlog:backlog-run` | Исполняет беклог задача за задачей |
| Навык `/backlog:backlog-template` | Проверяет, нужен ли операции беклог, называет критерии шаблона и принимает его прогоном `backlog check-template` |

Коды возврата у всех команд одни: `0` — сделано, `1` — расхождение названо либо ввод не позволяет
выполнить, `2` — ошибка вызова или окружения. Состав вызова целиком — `backlog <команда> --help`.

### Порождение беклога

```bash
backlog generate --operation sample-operation \
  --value target=проба --flag host-part
```

- `--operation` — имя операции, оно же имя файла шаблона;
- `--subject` — предмет беклога; без него предметом становится штамп прогона `YYYYMMDDHHMMSS`;
- `--value ключ=значение` — значение подстановки шаблона, повторяется по значению; каждому
  значению заводится парная подстановка `ключ_scalar` в виде, пригодном для фронтматтера;
- `--flag имя` и `--no-flag имя` — признак условного блока, взведённый и снятый; признак,
  не названный вовсе, порождение останавливает;
- `--root` и `--templates` — каталог следа и каталог шаблонов; умолчания — каталоги `backlog`
  и `templates` в корне проекта либо значения переменных `BACKLOG_ROOT` и `BACKLOG_TEMPLATES`.
  Корень проекта вход находит сам, поэтому прогон из подкаталога второго каталога следа
  не заводит.

Порождённый беклог не перезаписывается: повторный вызов над тем же адресом отвечает путём
лежащего файла и оставляет его неизменным.

### Исполнение беклога

Беклог исполняет агент по навыку `/backlog:backlog-run`: он читает порядок исполнения, идёт
по задачам сверху вниз и перед каждой сверяет признак «выполнено ранее» с состоянием —
при расхождении с отметкой верно состояние
([BKL-006](./rules/operation-backlog-rules.md#признак-исполнения)).

Отсюда два следствия. Повторный проход по исполненному беклогу состояния не меняет. Прерванная
операция продолжается с задачи, признак которой не выполнен, — без отката исполненного
и без порождения второго беклога.

Задача, последствия которой необратимы, несёт стоп-знак: исполнитель запрашивает подтверждение
непосредственно перед ней и называет последствия прямо. Утверждение беклога таким подтверждением
не является, а отказ прекращает исполнение
([BKL-007](./rules/operation-backlog-rules.md#стоп-знак-необратимой-задачи)).

### Проверка беклога

```bash
backlog lint backlog/<операция>/<предмет>/tasks.md
backlog verify backlog/<операция>/<предмет>/tasks.md
```

`lint` отвечает на вопрос, цела ли грамматика беклога: фронтматтер несёт версию шаблона
и указатель носителя порядка исполнения, каждая задача несёт строку проверки и признак
«выполнено ранее». `verify` добавляет к этому полноту исполнения: закрыты ли отметки
и заполнены ли подтверждения владельца — его прогоняют по завершении исполнения.

Расхождение проверка называет, но не правит: состояния она не видит.

## Свои операции

Образцовая операция поставки показывает грамматику формата — рабочие шаблоны проект пишет сам:
состав задач у каждой операции свой.

Шаблон — файл в каталоге `templates/`, и его имя есть имя операции, которое принимает
`--operation`. Образец лежит в `templates/sample-operation.md` после установки: по нему видно,
как записываются подстановки значений, условные блоки, строка проверки задачи и признак
«выполнено ранее». Версию шаблона называет сам шаблон первой строкой.

Состав задач правится **в шаблоне**. Порождённый беклог задним числом не правится: он назвал
версию шаблона, которой порождён, и правка действует на следующие операции, а не на состоявшиеся
([BKL-004](./rules/operation-backlog-rules.md#порождённое-не-правится)). Обстоятельство,
потребовавшее другого состава задач, правит шаблон — встретившееся однажды встретится снова.

Новый или правленый шаблон принимается прогоном `backlog check-template templates/<операция>.md`
([BKL-009](./rules/operation-backlog-rules.md#прогон-при-правке-шаблона)); провести через
приёмку целиком помогает навык `/backlog:backlog-template`.
